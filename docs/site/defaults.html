Runtime defaults

git-next is a replacement for Git, not a copy of it. The configuration it ships is therefore a product decision rather than whatever the upstream defaults happen to be: where a modern option is faster or easier without changing what a command means, it is turned on.

Every default lives in one file, packaging/runtime-defaults/gitconfig, and every one of them is exercised against the real binary by tools/check_runtime_defaults.py. A default is a promise about behaviour, and the checks are the claims in this document: if a value stops doing what is written here, the tool fails instead of the change reaching a workstation.

Scope of the measurements

Times are from one workstation (Windows, this repository's parent tree, git-next 0.3.0 on Git 2.54.0.windows.1) with a 5,000-file working tree, median of five runs, taken with no other build or benchmark running. They are reported as what they are: one machine, one tree size, one day. The file-count and process-count facts are reproducible anywhere.

Adding or changing a default

  1. Add the key to packaging/runtime-defaults/gitconfig, nowhere else. The payload configuration, the migration override and the evidence reuse check are rendered from that file or compared against it.
  2. Run python tools/check_runtime_defaults.py. It fails if the migration's literal has drifted from the fragment and if the new key cannot be shown to do something.
  3. Add a behavioural probe for it. A key that only has to be accepted needs no probe; a key that changes output or behaviour needs one that would fail if the value stopped being applied.
  4. Record the reason and the cost in this document, with the measurement you relied on.

A default is not eligible if it starts a process per repository. See the monitor for what that costs.

The thread values are the clearest case for behaviour over appearance. Both -1 and 0 look like "use the machine", one of them is a configuration that makes grep refuse to run, and the other is the fastest value measured. tools/check_runtime_defaults.py asserts the exit codes, which is the only way to tell them apart.

The file-system monitor is not a default

core.fsmonitor = true makes status faster. On 5,000 files it took the median from 292 ms to 241 ms, about 17%, and the cold run that starts the monitor costs 795 ms.

It is still not a default, because of what it leaves behind:

  • One daemon per repository, 12.1 MB each. Fifteen repositories measured 181.6 MB.
  • The daemon outlives the repository. Six repositories were created, used and deleted; six daemons were still alive one second later, and still alive fifteen seconds later. Nothing reaps them.

That last point is the one that matters. A population that only ever grows is the shape of the failure this product must not have, and a cache that survives its own repository is not a cache anyone can reason about. On this workstation the reaper found eight such daemons holding 67 MB, from repositories that no longer existed.

Someone who wants the speed can have it:

git config --global core.fsmonitor true
python tools/git_process_watchdog.py --daemons --apply

The second command terminates Git processes that have no parent and have been alive longer than two minutes, which is what a daemon looks like; a clone or a gc still has the process that asked for it and is left alone. It is the reason turning the monitor on is safe now rather than a slow leak.

maintenance.auto is off for the same reason: it runs git maintenance after ordinary commands, which is a process per command per repository.

Long paths

Three things have to agree before a path past MAX_PATH works, and the product controls two of them:

  1. The forwarder. A target at or beyond 260 characters is rebuilt with the extended-length marker (\\?\). The marker has to be added after normalisation, because an extended-length path is not normalised and a recorded root ending in a separator would leave a doubled one.
  2. The configuration. core.longpaths = true lives in the system configuration, so a repository operation accepts a long path even where a helper's Win32 manifest does not.
  3. The machine. HKLM\SYSTEM\CurrentControlSet\Control\FileSystem\LongPathsEnabled is an administrator setting, not a product default. tools/check_runtime_defaults.py reports it, and a machine where it is 0 needs an administrator to set it.

The ceiling

Nothing above slows a caller down, and nothing in a single Git process can stop a caller starting a thousand copies. Three layers cover that:

  • The forwarder refuses to start a copy of itself and stops a two-file cycle after four hops, so an entry point can never multiply itself.
  • tools/verify_windows_bridge_guard.py proves it inside a job object limited to 64 processes: self costs 1, cycle costs 5, and the previous forwarder hit the limit in both.
  • tools/git_process_watchdog.py is the machine-wide ceiling, and it terminates the newest excess because the oldest processes are the ones a person is waiting for. --daemons handles the slower leak described above.

Verifying and installing

python tools/check_runtime_defaults.py                  # agreement and behaviour
python tools/check_runtime_defaults.py --agreement-only # in a Linux container
python tools/install_runtime_defaults.py                # put them on this machine
python tools/install_runtime_defaults.py --plan         # show what is still missing
python tools/verify_repo_contract.py                    # every rule in AGENTS.md

The agreement half runs anywhere; the behavioural half needs a real binary. The last check in the run is the one that guards the incident this document came out of: after three repositories are used with the shipped defaults, no Git process is left behind.

install_runtime_defaults.py is the other half of shipping a default. It writes the migrated system configuration, relaunching itself elevated because that file is an administrator's; if consent is refused it falls back to the user's global configuration rather than leaving the defaults unapplied. It never overwrites a value a person chose, and it verifies by asking Git what each key resolves to afterwards, so "installed" means Git reports the value rather than a file having been written.
