# Full native compatibility core: integration report

## Scope and current status

The [fixed delivery ledger](DELIVERY_STATUS.md) selects this source-built core as the primary compatibility route. All five targets compile from one source identity and include owned runtimes, LFS and GCM. Windows x64, Linux x64 and emulated Linux ARM64 native-core checks pass; macOS evidence covers Mach-O/package/shell static checks without product execution. Windows ships the tested stable read profile described in [performance](PERFORMANCE.md). Final combined MSI, performance and workstation evidence is tracked in the delivery ledger. Historical receipts below retain their exact original scope.

The requested final product requires the full Git API and interaction surface, including rebase, stash, cherry-pick, revert, worktrees/submodules, hooks, signing, recovery and existing callers. The current Gitoxide/Russh preview remains incomplete. The user permits a different implementation when externally visible behavior remains compatible.

The native core is pinned to `git-for-windows/git` tag `v2.54.0.windows.1`, commit `2b8a3ab140826ac423c2845ef81d4c6ac4f7bf3c`, matching the reference generation. `packaging/native-core.lock.json` pins its official archive. `tools/prepare_native_core.py` prepares a dedicated source tree without workflows; `tools/integrate_native_core.py` verifies the complete original tree, applies hash-pinned patch chains and overlays, and generates the Chinese catalog and product identity. `tools/build_native_core.py` records compiled production targets without running product commands or tests. The installed preview/default Git have not changed.

The intended engine is rebuilt source belonging to git-next, with truthful git-next identity and its own runtime/helper paths. No installed official Git executable or original installation directory may be a runtime fallback. Internal invocations of git-next's own core and explicitly configured user hooks/filters/helpers must be audited separately from an installed-Git fallback. Default SSH must remain native and preserve host-key/certificate/agent/config guarantees; using a C core does not automatically close SSH compatibility gaps.

The Windows scope implementation now includes machine/user MSI, matching-hive legacy bridges, builtin executable aliases, protected shared configuration/components and the SYSTEM updater. The native version compatibility string retains `2.54.0.windows.1` and appends `.git-next.<product-version>` for Windows callers. Native update builtins delegate only to the owned updater and pass the already selected language. Compilation is recorded separately from earlier MSI bytes in the [scope checkpoint](../native-core/receipts/implementation-windows-scopes-20261020.json).

## Storage and behavior compatibility

Existing `.git` directories, refs, objects, packed files, indexes, reflogs, worktree/submodule metadata and LFS object bytes remain in place. No format conversion, repack, history rewrite, mass normalization or server cutover is authorized by engine integration. Existing object formats and repository extension negotiation remain contracts. Unsupported/new mandatory repository formats must reject before writes.

Git-next identity, `main` for new repositories, cross-platform LF defaults and English/Chinese interface selection are explicit product behavior. User attributes, binary files, configured hooks/filters and existing branch names retain their meaning. Machine/porcelain outputs remain stable. Native locale selection and `language get/set/list` must work across both engine and installation surfaces without translating user data.

The final installer must own all necessary runtime assets before the original Git is removed: client/helper executables, supported shell/script interpreters, certificate configuration, credential helpers, signing tools, templates, locale data and any accepted GUI/IDE integration. Build-time Git/sh/CMake dependencies do not prove runtime independence. Absolute-path callers and old helper/certificate paths need an explicit compatible migration and rollback plan; leaving a deleted old path in configuration is a failed migration.

## Build and licensing boundaries

The native POSIX build path now compiles the complete Linux x64 core with the pinned source dependencies and GnuTLS, including full script/template staging. Source permission metadata, generated Perl header bytes, installed script names and native image headers are build-time checks. No new core has run. Official LFS/GCM primary assets for all three POSIX targets are prepared separately. [The checkpoint](../native-core/receipts/implementation-posix-core-20261020.json) distinguishes those inputs from a complete independent runtime or accepted release.

macOS curl uses GnuTLS with Apple SecTrust for system certificate verification. The selected curl source no longer offers the removed Secure Transport backend; no backend is relabeled. The trust behavior follows the [curl certificate documentation](https://curl.se/docs/sslcerts.html). Actual macOS build, trust/keychain/SSH/caller behavior and performance require the Mac environment and D08/D09 evidence.

The upstream core's `COPYING` specifies GPL version 2. The Rust preview and its existing MIT license are retained as currently implemented. The observed Rust graph includes Apache-2.0-only components, including Russh and some Gitoxide dependencies; it must not be linked indiscriminately into a GPL-2.0-only core. Cross-component boundaries, chosen licenses and corresponding-source/notice delivery must be resolved and verified before distributing a combined product. A distinct process is not, by itself, sufficient evidence that every licensing obligation is met. No silent project relicensing is performed by source preparation.

The packaging gate must include complete required license texts, source provenance, applied patches and reproducible corresponding sources/build instructions for distributed copyleft components. See upstream `COPYING`, the pinned Cargo metadata, [GNU's license list](https://www.gnu.org/licenses/license-list.html), and its [aggregation guidance](https://www.gnu.org/licenses/old-licenses/gpl-2.0-faq.html#MereAggregation).

Windows native builds use the installed Visual Studio C toolchain. The native catalog replaces upstream's disabled MSVC gettext path, including positional printf handling and platform-dependent integer formats. The pinned upstream Chinese PO supplies 6226 messages, with 30 additional product messages. All compiler, runtime, package and acceptance evidence remain distinct. No upstream workflow is created, enabled or run.

## Owned Windows runtime preparation

`packaging/windows-runtime.lock.json` pins the official x64/ARM64 asset archives and their published SHA-256 values. `tools/fetch_windows_runtime.py` downloads/inventories the batch without executing it. `tools/prepare_windows_runtime.py` creates a new owned asset tree while excluding the upstream Git core/server/transport entrypoints. Retained scripts/interpreters, native SSH, GCM, Git LFS, signing tools, GUI launchers, certificate and license files keep their upstream ownership/provenance. MSYS virtual links are materialized in their regular-file format and retain the System attribute. No original local Git installation is used as the runtime asset source.

The raw x64/ARM64 asset trees do not contain a Git engine. `tools/assemble_native_windows.py` now integrates the x64 owned core/helper entrypoints, relocated paths, package configuration and documents into a new hash-manifested distribution. `packaging/native_msi.py`, selected by `packaging/build_msi.py --distribution`, compiles its entire payload without executing product commands. Other platform assembly and corresponding-source delivery remain open. Windows uses one declared primary owned SSH helper; the earlier Russh preview is not a fallback to it. Explicit `GIT_SSH`, `GIT_SSH_COMMAND`, configured helpers and hooks retain their normal contract. Missing owned assets must fail rather than searching the original Git directory.

`tools/prepare_windows_iconv.py` statically checks the pinned DLL's machine/export ABI and creates x64/ARM64 MSVC import libraries without loading the DLL. Its C bridge transfers error codes from the DLL's MSVCRT to the core's CRT, including conversion-buffer exhaustion and invalid sequences. GNU iconv source/license delivery and final encoding/failure conformance remain package/acceptance gates. Preparation and static PE inspection establish no runtime result.

## Native Windows TLS and public suffixes

The primary core links source-built curl 8.23.0 with native Schannel and statically linked nghttp2 HTTP/2. The [static dependency checkpoint](../native-core/receipts/implementation-static-runtime-20261020.json) records 48 inspected owned PE images and both optional provider export tables without loading them. `tools/prepare_windows_psl.py` pins the producer's libpsl 0.21.5 DLL ABI and recursively inventories its owned dependencies; native curl uses this API for cookie public-suffix checks. The ABI header retains its upstream MIT notice. The assembler places required DLLs beside each native entrypoint, including the libiconv dependency. No DLL is loaded during this preparation.

Explicit `http.sslBackend=openssl` or `CURL_SSL_BACKEND=openssl` selects the real pinned OpenSSL curl provider through a native ABI function table. The adapter does not rename Schannel, spawn a transport for each request or search an installed Git. Host-CRT stream callbacks keep the optional DLL's CRT from receiving host `FILE` pointers; provider configuration/modules preserve their relocated producer directory layout. Explicit environment overrides remain authoritative.

`packaging/tls-providers.lock.json` and the compiled `git-next-tls-pins.h` identify all 17 provider files per Windows architecture, the producer archive SHA-256 and entrypoint. This provider DLL is **excluded from the public Git-next payload**. The installed `components/install-tls-provider.ps1` independently downloads the pinned official producer archive on first explicit selection, or accepts `-Archive` for offline preparation. Downloads use the existing verified mirror transport. Each component file is checked before an atomic install; altered existing components fail without replacement. `GIT_NEXT_COMPONENT_HOME` chooses an absolute private component directory, and `GIT_NEXT_TLS_AUTO_INSTALL=0` disables automatic acquisition. TLS components, caches and login data are outside the MSI product tree.

Before old-Git removal the migration procedure must prepare any required legacy TLS backend, including offline use. Provider acquisition, API behavior, relocation, integrity failures and CRT/encoding compatibility are all D08 checks and have not run. The actual license/linking/source boundaries still belong to D07; private component acquisition is not a claim that arbitrary combined redistribution is permitted.

## Migration, rollback, capacity and performance

Integration is staged outside installed commands. The previous accepted preview and original Git remain available while the final scope is implemented. Rollback selects the previous complete owned package and restores only migration-owned command/PATH/shortcut/task state; repositories and user login data require no storage migration. A successful MSI build does not authorize activation or removal.

Additional source/build/runtime assets increase download, cache and disk requirements; final packaging must record their actual sizes and ownership. Startup, status, object reads, network operations, memory and upgrade latency must be measured on the final optimized bytes in one paired batch. Reusing a mature engine is a compatibility strategy, not evidence of a speedup. The retained Rust directory-inventory experiment is also unaccepted until that batch establishes correctness and a material benefit.

The release remains one consolidated local-gated release after full requirement coverage, supported platform packages, checksums/signatures, preserved-login migration, MSI/update rollback and actual Windows caller takeover pass. No parity flag is changed by preparing or compiling this core.

## Migrated system configuration contract

Windows runtime configuration now has a separate [default/active lifecycle](UPDATES.md): the installer initializes active `etc` files from immutable packaged defaults, migration puts preserved settings at the actual SSH/shell/signing paths, and private snapshots support failure/rollback. The optional TLS provider uses an explicitly configured `OPENSSL_CONF` first, otherwise the active owned native-prefix config before its pinned component default. `OPENSSL_MODULES` still defaults to the owned component modules. No original Git/OpenSSH executable is selected as a fallback.

POSIX source dispatch is now explicit too: SSH and Git's command shell resolve `runtime/usr/bin/ssh` and `runtime/usr/bin/sh`, helpers/templates/docs use `runtime/usr`, and the owned bin directory precedes inherited PATH. Missing owned helpers fail; explicit user helper overrides retain Git semantics. These POSIX patches are integrated source inputs, not compiled platform/runtime acceptance. Remaining runtime assembly/build recipes and final platform packages keep D02/D07 open.

`git_system_config()` now selects an existing `system.gitconfig` beside git-next's language settings, after an explicit `GIT_CONFIG_SYSTEM` override and before the ordinary product default. Missing files fall back normally; inaccessible migration files fail rather than silently losing effective authentication/configuration settings. This makes `git config --system` writes affect the active migrated file, with the ordinary Git lock/atomic update semantics. The migration script creates it only for a final accepted handoff. The additive file/pointer and rollback, capacity and caller effects are documented in [Windows takeover](TAKEOVER.md). No repository/LFS layout changes occur.
