Runtime defaults

git-next is a replacement for Git, not a copy of it. The configuration it ships is therefore a product decision rather than whatever the upstream defaults happen to be. Complete results and predictable resource use across concurrent game projects take priority over maximizing one command's worker count.

Every default lives in one file, packaging/runtime-defaults/gitconfig, and every one of them is exercised against the real binary by go -C tools/devtool run . check-runtime-defaults. A default is a promise about behaviour, and the checks are the claims in this document: if a value stops doing what is written here, the tool fails instead of the change reaching a workstation.

Scope of the measurements

Times are from one workstation (Windows, this repository's parent tree, git-next 0.3.0 on Git 2.54.0.windows.1) with a 5,000-file working tree, median of five runs, taken with no other build or benchmark running. They are reported as what they are: one machine, one tree size, one day. The file-count and process-count facts are reproducible anywhere.

The current Windows read defaults prioritize complete results over those historical timings. On 2026-10-23, the same frozen 1.0.3 native binary and a generated 4,000-file repository returned only 3,999 files in round 21 with fscache/preloading enabled and automatic index/grep threads. The five-setting serial control below completed all 30 grep/status rounds. This isolates the configuration effect; it does not establish the internal cause or a throughput comparison. See the bounded read-safety evidence.

Adding or changing a default

  1. Add the key to packaging/runtime-defaults/gitconfig, nowhere else. The payload configuration, the migration override and the evidence reuse check are rendered from that file or compared against it.
  2. Run go -C tools/devtool run . check-runtime-defaults. It fails if the migration's literal has drifted from the fragment and if the new key cannot be shown to do something.
  3. Add a behavioural probe for it. A key that only has to be accepted needs no probe; a key that changes output or behaviour needs one that would fail if the value stopped being applied.
  4. Record the reason and the cost in this document, with the measurement you relied on.

A default is not eligible if it starts a process per repository. See the monitor for what that costs.

These five settings apply to the shipped Windows profile and takeover defaults. POSIX packages retain native automatic index/grep budgets. The six common resource settings above also ship in POSIX packages, rendered from the same fragment without copying the Windows read-safety switches. User, repository and command-line settings keep their normal precedence. The read-thread gate verifies the shipped values against the authoritative fragment and requires complete results in every one of 30 rounds; timing a command that omitted files is not an accepted performance sample.

The file-system monitor is not a default

core.fsmonitor = true makes status faster. On 5,000 files it took the median from 292 ms to 241 ms, about 17%, and the cold run that starts the monitor costs 795 ms.

It is still not a default, because of what it leaves behind:

  • One daemon per repository, 12.1 MB each. Fifteen repositories measured 181.6 MB.
  • The daemon outlives the repository. Six repositories were created, used and deleted; six daemons were still alive one second later, and still alive fifteen seconds later. Nothing reaps them.

That last point is the one that matters. A population that only ever grows is the shape of the failure this product must not have, and a cache that survives its own repository is not a cache anyone can reason about. On this workstation the reaper found eight such daemons holding 67 MB, from repositories that no longer existed.

Someone who wants the speed can have it:

git config --global core.fsmonitor true
go -C tools/devtool run . git-process-watchdog --daemons --apply

The second command terminates Git processes that have no parent and have been alive longer than two minutes, which is what a daemon looks like; a clone or a gc still has the process that asked for it and is left alone. It is the reason turning the monitor on is safe now rather than a slow leak.

maintenance.auto is also off: it can start transient git maintenance children after ordinary commands, multiplying work across active repositories. It does not create the same resident daemon as fsmonitor. Run explicit maintenance when appropriate for a long-lived repository; disabling automatic maintenance does not maintain it for you.

Common game-project resource policy

The previous fragment omitted maintenance.auto=false even though this document said it was disabled. The shared fragment now expresses that policy, and the actual command probes compare both disabled and explicitly enabled maintenance. They also verify manual maintenance, generated pack contents, cache-size parsing and the manifest-bound bundled LFS helper's effective worker count.

The three memory knobs are not independently measured process limits. A pack thread has its own search window, a packing process has its own delta cache, and several repositories can run several processes. Large individual objects and the index can exceed those budgets. Git's k/m/g units are binary; the exact setting semantics are documented in the Git configuration reference. LFS concurrency applies to each helper process; the pinned helper's upstream default is eight workers. Git LFS 3.7.1 configuration.

Explicit per-repository values and git -c keep their normal priority. Installation does not rewrite repository configs, histories or Git/LFS storage. See game projects for independent repositories, nested Unity/Unreal project roots and deliberate maintenance.

The 2026-10-25 profile measurements use the same native 1.0.3 bytes on Windows x64 with the original and selected configurations. With four repositories each holding eight 16 MiB assets/two revisions, first concurrent packing moves from 1519.21 to 440.49 MiB peak job commit and 29.011 to 6.920 seconds; compressed pack byte counts remain identical. The one-64-MiB-asset control does not reduce peak memory, and some reused-pack timings regress. LFS whole-tree peak commit has a median of about 196 versus 175 MiB across two AB/BA samples per profile. These are joint-profile effects, not per-key causal measurements or RSS limits. Full scope, raw phases and costs are retained in performance.

Long paths

Three things have to agree before a path past MAX_PATH works, and the product controls two of them:

  1. The forwarder. A target at or beyond 260 characters is rebuilt with the extended-length marker (\\?\). The marker has to be added after normalisation, because an extended-length path is not normalised and a recorded root ending in a separator would leave a doubled one.
  2. The configuration. core.longpaths = true lives in the system configuration, so a repository operation accepts a long path even where a helper's Win32 manifest does not.
  3. The machine. HKLM\SYSTEM\CurrentControlSet\Control\FileSystem\LongPathsEnabled is an administrator setting, not a product default. go -C tools/devtool run . check-runtime-defaults reports it, and a machine where it is 0 needs an administrator to set it.

The ceiling

These defaults deliberately trade some single-command parallelism and cache capacity for predictable concurrent use. They cannot stop an arbitrary caller starting a thousand copies. Separate process controls cover entry-point recursion and runaway processes:

  • The forwarder refuses to start a copy of itself and stops a two-file cycle after four hops, so an entry point can never multiply itself.
  • go -C tools/devtool run . verify-windows-bridge-guard proves it inside a job object limited to 64 processes: self costs 1, cycle costs 5, and the previous forwarder hit the limit in both.
  • go -C tools/devtool run . git-process-watchdog is the machine-wide ceiling, and it terminates the newest excess because the oldest processes are the ones a person is waiting for. --daemons handles the slower leak described above.

Verifying and installing

go -C tools/devtool run . check-runtime-defaults                  # agreement and behaviour
go -C tools/devtool run . check-runtime-defaults --agreement-only # in a Linux container
go -C tools/devtool run . install-runtime-defaults                # put them on this machine
go -C tools/devtool run . install-runtime-defaults --plan         # show what is still missing
go -C tools/devtool run . verify-repo-contract                    # every rule in AGENTS.md

The agreement half runs anywhere; the behavioural half needs a real binary. The last check in the run is the one that guards the incident this document came out of: after three repositories are used with the shipped defaults, no Git process is left behind.

go -C tools/devtool run . install-runtime-defaults is the other half of shipping a default. It writes the migrated system configuration, relaunching itself elevated because that file is an administrator's; if consent is refused it falls back to the user's global configuration rather than leaving the defaults unapplied. It never overwrites a value a person chose, and it verifies by asking Git what each key resolves to afterwards, so "installed" means Git reports the value rather than a file having been written.
